Сложность: Средний

Отправьте выбранную локальную историю в собственный репозиторий GitHub по SSH и получите её во второй обычной локальной копии через SSH clone. Сохраните исходную вершину main, достижимые коммиты и их содержимое.

Маршрут — PowerShell 7/Windows либо fish/Linux. Нужны Git, доступ к GitHub и выбранный SSH-клиент с пригодным ключом. Общие правила подготовки и проверки архива.

Самостоятельный вход

Комплект содержит готовый обычный репозиторий:

versioning/
└── project/
    ├── .git/
    ├── README.md
    └── catalog.tsv

README объясняет каталог оборудования по помещениям и столбцы code и room. В catalog.tsv эти столбцы разделены TAB, кодировка — UTF-8. Готовая история состоит из двух линейных коммитов: корневого S0 и его единственного потомка S1. В S0 есть meter-01 в помещении 201. В S1 добавлен meter-02 в помещении 203; первая запись и README сохранены. main выбирает S1, индекс и рабочее дерево чисты. Remote, веток разработки, тегов, коммитов слияния и секретов в комплекте нет. S0/S1 — обозначения предоставленных состояний.

Можно выбрать собственный предыдущий локальный проект: обычный репозиторий с выбранной main, доступной исходной историей и чистым состоянием. Расположите выбранный репозиторий в versioning/project, сохранив .git. Зафиксируйте его исходную вершину main для дальнейшего сравнения. Готовая история из комплекта позволяет начать эту задачу самостоятельно.

Подготовка доступа

Используйте личный аккаунт GitHub либо зарегистрируйте его по инструкции подготовки аккаунта. Подтвердите почту, настройте защиту входа и сохраните способы восстановления в личном хранилище. Сведения автора коммитов выбираются с учётом видимости почты в истории.

Используйте пригодную существующую пару SSH-ключей либо создайте новую под свободным именем, сохранив прежние ключи. Зарегистрируйте открытый ключ в своём аккаунте. В Windows Git и проверочная команда должны использовать согласованный системный Windows OpenSSH со службой ssh-agent. Объяснение роли ключа, парольной фразы и агента находится в подготовке Windows и fish/Linux.

При первом подключении сверяйте ключ сервера с официальными отпечатками GitHub. При несовпадении выясните причину до продолжения. Проверка соединения в режиме ssh -T должна распознать ваш ожидаемый GitHub-аккаунт. Прочитайте сообщение и объясните штатный код 1: аутентификация успешна, интерактивная оболочка не предоставляется. Назначение проверки описано в инструкции GitHub. Закрытый ключ, парольная фраза, токены и коды восстановления в проект и предъявляемые материалы не включаются.

Отправка и получение

Создайте пустой учебный репозиторий GitHub с видимостью Public либо Private. Настройте SSH remote и отправьте исходную main. Проверьте на GitHub отправленную вершину и файлы.

Выполните SSH clone с GitHub в versioning/verification. Это обычная копия с собственным .git, выбранной main и чистым состоянием. Отправленная вершина main, main в project и main в verification совпадают. Во второй копии доступны все коммиты, связи родителей и деревья, достижимые из исходной вершины выбранного входа. Сопоставьте историю и содержимое обеих копий. Для комплекта это S0/S1; для собственного проекта — весь его исходный граф, включая слияния, если они есть.

Реальные SSH push и SSH clone предъявляются коротким сохранённым выводом существенных операций либо демонстрацией преподавателю. Локальный remote или копирование папки не выполняют требование обмена через GitHub.

Пояснение и предъявление

Создайте versioning/explanation.md. Укажите ОС, оболочку, версию Git и выбранный SSH-клиент, вид выбранного входа и его исходную вершину main. Запишите URL GitHub, видимость, распознанный SSH-аккаунт и результат отправки; расположение verification, её origin, полученную вершину и результат сравнения графа и файлов. Объясните проверку сервера, сообщение аутентификации и код 1. Историю выбранного входа заново создавать и описывать её авторство не требуется.

Предъявите URL и ZIP либо tar.gz каталога versioning с project, verification и explanation.md. Сохраните оба каталога .git целиком, с историей, ссылками, индексом и конфигурацией, вместе с рабочими файлами. После извлечения в обеих копиях должны читаться .git/HEAD, исходная история и одна отправленная вершина main; рабочее состояние чистое, содержимое соответствует сохранённым деревьям. На разборе покажите сравнение истории и признаки внешнего обмена, сохранив секретные данные закрытыми.

Для Public преподаватель может открыть репозиторий непосредственно. Для Private предоставьте доступ преподавателю либо согласуйте показ истории и внешнего обмена вместе с локальным архивом. Видимость менять ради предъявления не требуется.

Подготовка: обмен историей, проверка SSH-доступа, удалённый репозиторий и упаковка обеих копий.

Открытые примеры

Отправка и получение всей выбранной истории

Исходный project чист, выбрана main, её вершина записана. Доступ по SSH подготовлен, собственный репозиторий GitHub пуст. После настоящего SSH push в GitHub и SSH clone оттуда в verification исходная, серверная и полученная вершины main совпадают. В verification доступны все исходные достижимые коммиты с теми же родителями и деревьями. У обеих локальных копий собственные .git, выбрана main, индекс и рабочее дерево чисты.

Для готового входа сохраняются S0/S1 с catalog.tsv и две записи оборудования в S1. Для собственного проекта сохраняется его исходный граф, включая имеющиеся слияния; количество коммитов определяется выбранной историей. Допустимы Public и Private. Сохранённый вывод существенных операций либо демонстрация подтверждают GitHub и транспорт SSH.

Успешная аутентификация с кодом 1

Ключ сервера сверен с официальными отпечатками, выбранный SSH-клиент использует пригодный ключ ожидаемого аккаунта. Проверка в режиме ssh -T завершается с кодом 1 и сообщает об успешной аутентификации ожидаемого GitHub login и отсутствии интерактивной оболочки. Сообщение, login и код оцениваются вместе. Другой login или отказ аутентификации означают, что требуемый доступ ещё не подтверждён. Право записи в конкретный репозиторий и получение истории показывает внешний обмен из первого примера.

Оба примера требуют наблюдения настоящего соединения. Адрес remote и совпадение локальных файлов устанавливают только часть результата. Если внешнее соединение предъявить не удалось, эта часть проверки остаётся открытой. Секретные значения сохраняются в личном хранилище.
