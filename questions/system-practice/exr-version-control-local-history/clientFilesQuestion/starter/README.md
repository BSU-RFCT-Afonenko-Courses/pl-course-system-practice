<a id="exr-version-control-local-history"></a>

Создайте историю проекта измерений с двумя самостоятельными изменениями. Объедините их операцией merge и разрешите конфликт, сохранив смысл обоих изменений.

Нужен Git; маршрут — PowerShell 7/Windows либо fish/Linux. Имя рабочей ветки выберите самостоятельно. [Общие правила подготовки и проверки архива](https://bsu-rfct-afonenko-courses.github.io/System-Practice/tasks/index.html#sec-bank).

<div>

<a id="исходный-проект"></a>

### Исходный проект

</div>

Комплект содержит исходные файлы:

``` text
versioning/
└── project/
    ├── README.md
    ├── criteria.txt
    └── measurements.tsv
```

В `project` отсутствует `.git`; историю создаёте вы. Это текстово-табличный проект, программа обработки не требуется.

| Файл | Исходное содержимое |
|----|----|
| `criteria.txt` | Единственная строка `latency_limit = 25 ms` |
| `measurements.tsv` | Столбцы `sensor`, `latency_ms`; записи `north`, `18` и `south`, `28`; разделитель TAB |
| `README.md` | Назначение проекта; измерения выражены в миллисекундах; в отчёт включаются значения, не превышающие порог из criteria.txt |

Кодировка файлов — UTF-8; окончания LF и CRLF допустимы. Состав, порядок и значения `measurements.tsv`, включая единицу ms, сохраняются на протяжении работы. Имя, почту, даты и сообщения своих коммитов выберите самостоятельно; сообщения должны описывать изменения.

<div>

<a id="расходящиеся-состояния"></a>

### Расходящиеся состояния

</div>

Инициализируйте репозиторий в `project` с основной веткой `main`, задайте сведения об авторе и сохраните начальный снимок трёх файлов. Для объяснения назовём этот коммит A.

Подготовьте две самостоятельные линии:

- В основной линии увеличьте порог до `30 ms`. Обозначим состояние B.
- В отдельной рабочей ветке выразите исходные 25 ms в секундах: `latency_limit = 0.025 s`. Дополните README пояснением, что порог записывается в секундах. Обозначим состояние F.

В момент соединения B и F должны расходиться: обе продолжают A, ни одна не включает другую. В их `criteria.txt` читаются указанные разные изменения.

Перед одним из коммитов сохраните короткое наблюдение подготовки: рабочее содержимое файла, подготовленное изменение и выбранный снимок. По status и соответствующим diff объясните, какое содержимое попадёт в обычный commit. Достаточен короткий сохранённый след либо показ на разборе; полный журнал команд не требуется.

<div>

<a id="согласованный-результат"></a>

### Согласованный результат

</div>

Соедините линии операцией merge с двухродительским коммитом слияния. Разрешите возникший конфликт `criteria.txt`, сохранив увеличение порога до 30 ms и его запись в секундах. Назовём коммит слияния D.

Итоговые свойства:

- `criteria.txt` содержит `latency_limit = 0.030 s`; запись `0.03 s` равнозначна и допускается.
- README сохраняет назначение исходных измерений и поясняет единицу записи порога; `measurements.tsv` содержит прежние измерения в ms.
- D имеет двух родителей, сохраняющих обе расходившиеся линии. A, B, F и D достижимы из итоговой `main`.
- Рабочая ветка сохранена на F либо на включённом в main продолжении F.
- HEAD выбирает `main`; индекс и рабочее дерево совпадают с её снимком. Маркеров конфликта и незавершённого слияния нет.

A, B, F, D — обозначения для объяснения, одноимённые теги создавать не требуется. Дополнительные содержательные коммиты допустимы при сохранении состояний, расхождения и обеих линий родителей. Порядок родителей D не фиксируется. Линейная история без требуемого коммита слияния не выполняет условие.

<a id="пояснение-и-предъявление"></a>

### Пояснение и предъявление

</div>

Создайте `versioning/explanation.md` рядом с `project`. Укажите ОС, оболочку, версию Git, собственные идентификаторы A/B/F/D, имя рабочей ветки и родителей D. Объясните наблюдение подготовки снимка, исходные стороны конфликта и итоговую величину через соотношение 1000 ms = 1 s. Покажите, как итоговая строка сохраняет оба изменения.

Создайте самодостаточный bundle истории: из каталога `project` выполните `git bundle create ../history.bundle --all`. Сохраните в одном ZIP или tar.gz каталог `versioning` с `history.bundle`, рабочими файлами `project` и прежним `explanation.md`.

При проверке сдачи в новой пустой области восстановите историю из `history.bundle`: должны читаться A/B/F/D, обе линии и родители D, итоговая main и сохранённая рабочая ветка. Внешний исходный репозиторий для этого не требуется. Сопоставьте файлы восстановленных снимков с условием.

Bundle переносит коммиты и ссылки. Исходный выбор HEAD, индекс и рабочее дерево предъявите отдельно: короткий след либо демонстрация должны показать итоговый status и сравнения HEAD → индекс → рабочее дерево. Чистота новой проверочной копии не устанавливает чистоту исходной работы. Применение merge и разрешение конфликта также проверяются по имеющемуся короткому следу либо показу и пояснению; двух родителей D для этого недостаточно. На разборе покажите чтение файла из истории, граф родителей и подготовку снимка.

<a id="согласованный-порог-и-сохранённые-линии"></a>

#### Согласованный порог и сохранённые линии

</div>

В A порог равен 25 ms, измерения — north/18 и south/28 в ms. Расходящиеся B и F задают соответственно 30 ms и 0.025 s с пояснением секунд. После слияния в D `criteria.txt` содержит `latency_limit = 0.030 s` либо `latency_limit = 0.03 s`: увеличенный порог выражен в новой единице. README объясняет единицу, измерения сохранены.

При чтении bundle доступны снимки и ссылки: у D два родителя, сохраняющие обе линии, A/B/F/D достижимы из `main`, рабочая ветка сохранена на F либо на включённом в `main` продолжении F. Исходный HEAD на `main` и чистоту исходного индекса и рабочего дерева показывает короткий след либо демонстрация. Применение merge, разрешение конфликта и подготовка снимка также предъявляются по наблюдениям и пояснению.

<div>

<a id="короткая-запись-того-же-результата"></a>

#### Короткая запись того же результата

</div>

В решении с теми же отношениями A/B/F/D итоговая строка может иметь вид `latency_limit = 0.03 s`, а тексты — окончания LF либо CRLF. При чтении порога получается та же величина 30 ms; значения и порядок измерений сохраняются. Требования к слиянию, веткам и чистоте действуют для обоих вариантов записи. Достаточно одного допустимого решения.

Идентификаторы, имя рабочей ветки, даты и сообщения берутся из вашей работы. Дополнительные содержательные коммиты и любой порядок родителей D допустимы при сохранении требуемых отношений истории.

# Слияние изменений порога

Выберите PowerShell 7 на Windows либо fish на Linux. Нужны Git и текстовый редактор. Распакуйте комплект в новую доступную папку и найдите `versioning/project`: исходные три файла предоставлены без `.git`.
