<a id="exr-project-maintenance-release"></a>

Добровольный проект продолжает три обязательные лабораторные. Подготовьте выпуск небольшого проекта отчёта: получите поступившую историю, согласуйте расходящиеся изменения, примите патч на выбранной базе и передайте именованную проверенную версию.

Нужен Git; локальный маршрут — PowerShell 7/Windows либо fish/Linux. [Общие правила подготовки и проверки архива](https://bsu-rfct-afonenko-courses.github.io/System-Practice/tasks/index.html#sec-bank). Подготовка — [введение к проекту](https://bsu-rfct-afonenko-courses.github.io/System-Practice/practice/project-maintenance.html#/sec-maintenance-intro), [теория сопровождения](https://bsu-rfct-afonenko-courses.github.io/System-Practice/theory/project-maintenance.html#sec-project-maintenance) и [справочник](https://bsu-rfct-afonenko-courses.github.io/System-Practice/handbook/project-maintenance.html#sec-maintenance-reference).

<div>

<a id="sec-maintenance-task-input"></a>

### Исходный проект

</div>

Распакуйте [стартовый архив](resources/materials/project-maintenance-start.zip) в новую папку:

``` text
maintenance/
├── work/                  обычный репозиторий с .git
├── shared.git/            bare-репозиторий обмена
└── incoming/
    └── review.patch
```

В work текущая main и тег start выбирают M, тег base — A. Индекс и рабочее дерево чисты. В shared.git main и тег incoming выбирают F, тег base — A. Оба коммита M и F имеют единственного родителя A:

``` text
work:       main ──> M ──┐
                        v
                        A <── base
                        ^
shared.git: main ──> F ──┘
```

Настройте в work собственные имя и почту автора, а также remote origin с адресом соседнего shared.git. Используйте переносимый относительный путь от work, например ../shared.git: он сохранится при переносе всей maintenance. Сохраните исходные коммиты, значения тегов base/start/incoming и входной review.patch. Личные аккаунты и сетевые ключи для обмена между этими каталогами не требуются.

<div>

<a id="назначение-изменений"></a>

### Назначение изменений

</div>

Проект задаёт параметры отчёта в report.ini. Его три строки идут в порядке format, columns, decimal; каждая имеет вид `имя=значение`.

| Версия | format | columns      | decimal |
|--------|--------|--------------|---------|
| A      | text   | code         | dot     |
| M      | csv    | code,value   | dot     |
| F      | text   | code,quality | dot     |

Линия M перевела отчёт в CSV и добавила числовое значение. Линия F добавила признак качества записи. Новый выпуск должен сохранить оба назначения: CSV с колонками code,value,quality в указанном порядке и десятичной точкой dot.

В исходных версиях instructions.txt содержит строку:

``` text
Проверьте входные данные.
```

Патч добавляет следующее указание: `Сохраните признак качества.` Он подготовлен для A. Во всех исходных снимках также есть .gitattributes с `* text=auto eol=lf`; других отслеживаемых файлов нет. Исходные тексты — UTF-8 без BOM с завершающим LF.

<div>

<a id="sec-maintenance-task-patch"></a>

### Отдельная линия патча

</div>

Проверьте применимость review.patch средствами Git и примените его. Сохраните изменение отдельным обычным коммитом P с единственным родителем A. В P изменён только instructions.txt согласно патчу; два других файла сохраняют содержимое A. Выберите имя рабочей ветки и оставьте эту ветку на P для обращения к исходному предложению.

Это требование сохраняет проверенное предложение в том состоянии проекта, для которого оно подготовлено. Итоговый выпуск должен включить P по родительским связям. Определите базу ветки, момент фиксации патча и порядок его объединения с другими изменениями.

<div>

<a id="sec-maintenance-task-result"></a>

### Согласование отчёта

</div>

Получите историю shared.git через fetch. Объедините расходящиеся линии M и F операцией merge, разрешив конфликт report.ini по назначениям двух изменений. Включите также линию P. Порядок объединения, промежуточные ветки и границы последующих коммитов выбираете вы.

Итоговая main выбирает коммит R. Обязательные файлы его снимка:

| Файл | Требуемое содержимое |
|----|----|
| .gitattributes | Исходная строка политики текстовых файлов |
| report.ini | `format=csv`, `columns=code,value,quality`, `decimal=dot` на трёх строках |
| instructions.txt | Исходное указание и новая строка из патча |
| VERSION | Единственная строка `2.0` |
| CHANGELOG.md | Заголовок с номером 2.0 и собственное описание изменений для получателя |

Итоговый instructions.txt:

``` text
Проверьте входные данные.
Сохраните признак качества.
```

В CHANGELOG.md объясните сохранённые назначения двух линий отчёта и добавленное правило инструкции. Формулировки выбираете самостоятельно. Дополнительные обычные текстовые документы в корне проекта или вложенных каталогах допустимы. Файлы имеют кодировку UTF-8 без BOM и завершающий перевод строки. Окончания LF и CRLF допустимы; политика .gitattributes нормализует текст при подготовке снимка. Двоичные вложения и символические ссылки в состав этого текстового проекта не включаются. Исполняемый бит обычных файлов не является отдельным требованием; индекс и рабочие файлы должны совпадать со снимком.

R сохраняет M, F и P как предков. Коммиты слияния связывают расходившиеся линии; исходные коммиты сохраняются. Дополнительные содержательные коммиты допустимы. Порядок родителей слияний, сообщения, даты и ID собственных коммитов свободны; сообщения описывают изменения. Переписанная линейная история без исходных M/F/P и требуемых слияний условие не выполняет.

В сдаваемом work HEAD выбирает main/R; индекс и рабочее дерево чисты, незавершённых операций и маркеров конфликта нет. Выбранная ветка патча по-прежнему указывает на P. Число остальных веток не фиксируется.

<div>

<a id="sec-maintenance-task-release"></a>

### Именованный выпуск

</div>

Создайте аннотированный тег v2.0 на R с содержательной аннотацией. Передайте main и тег через origin в shared.git обычным push. У получателя должны находиться тот же R и тот же объект тега v2.0; исходные base/incoming сохраняются. Цифровая подпись тега не требуется.

Поместите рядом с work:

- **release.patch** — разность файлов start/M → v2.0, созданную Git. На чистом снимке start проверка применимости проходит, применение воспроизводит все файлы R, включая новые документы выпуска.
- **report-2.0.zip** — архив дерева v2.0, созданный Git. Под единым каталогом report-2.0/ находятся все отслеживаемые файлы R с тем же содержимым; истории .git в архиве выпуска нет.
- **explanation.md** — краткое пояснение ваших решений и проверок.

Время элементов ZIP, степень сжатия и служебные хеши заголовков патча не фиксируются. Воспроизводимость устанавливается по исходной версии, составу и содержимому результата.

<div>

<a id="обоснование-решения"></a>

### Обоснование решения

</div>

В explanation.md укажите свою ОС, оболочку, версию Git, имя ветки патча и собственные ID P/R. Объясните по коротким наблюдениям:

1.  Что изменилось после fetch и где находится origin/main.
2.  Какие требования двух сторон сохранены разрешением конфликта.
3.  Почему P продолжает A; как проверен и применён входной патч.
4.  Какие родительские связи сохраняют M/F/P в итоговой main.
5.  Как установлены одинаковые R и объект тега у получателя.
6.  На какой базе проверен release.patch и как сопоставлен архив с v2.0.

Для обязательных приёмов — fetch, merge с разрешением конфликта, проверки и применения патча, создания аннотированного тега, push и git archive — сохраните краткие результаты существенных действий либо покажите их на разборе. Полный журнал терминала не требуется. Файлы и история позволяют проверить результат; выбранные наблюдения дополняют его сведениями о применённых приёмах.

<div>

<a id="sec-maintenance-task-submit"></a>

### Сдача

</div>

Предъявите архив **всей maintenance** в формате ZIP или tar.gz. В него входят work с собственным каталогом .git, полный shared.git, неизменённый incoming/review.patch и три созданных материала. [Полная упаковка](https://bsu-rfct-afonenko-courses.github.io/System-Practice/handbook/project-maintenance.html#sec-reference-maintenance-package) сохраняет историю и позволяет проверить её после извлечения.

После извлечения Git должен читать историю обоих репозиториев; work сохраняет R, чистое состояние и ветку P, shared.git — R и аннотированный v2.0. Проверьте исходные теги, материалы выпуска и пояснение из извлечённой папки.

На разборе устанавливаются смысл согласованного отчёта, выбор базы, отношения истории и воспроизводимость передаваемой версии.

### Открытые примеры

<div>

<a id="передача-именованного-выпуска"></a>

#### Передача именованного выпуска

</div>

В `work` подготовлен R по условию, `main` выбирает R, аннотированный `v2.0` обозначает R. Исходные A/M/F и линия P сохранены, а `main` в `shared.git` ещё выбирает F. Адрес `origin` указывает относительным путём на соседний `shared.git`.

После обычного push `main` и `v2.0` через `origin` у получателя находятся тот же R и тот же объект аннотированного тега. В `shared.git` сохраняются `base` на A и `incoming` на F; в `work` — `base` на A и `start` на M. `work` остаётся чистым. Сопоставьте реальные идентификаторы коммита и объекта тега в обеих копиях; предъявите результат push, значения ссылок и тип тега либо покажите их на разборе. Совпадение объектов подтверждает результат передачи, наблюдение push — применённый приём.

<div>

<a id="включение-дополнительного-документа-в-выпуск"></a>

#### Включение дополнительного документа в выпуск

</div>

Допустим, в R вместе с обязательными файлами включён `docs/quality.txt` с одной строкой `CSV сохраняет значение и признак качества.` и завершающим переводом строки. Созданы `release.patch` от M к R и `report-2.0.zip` дерева R с префиксом `report-2.0/`.

Проверка применимости и применение патча на отдельном чистом снимке `start`/M воспроизводят весь состав и содержимое R, включая новый документ. В ZIP он читается по пути `report-2.0/docs/quality.txt` с тем же содержимым; обязательные файлы также совпадают с R, `.git` отсутствует. Время элементов и степень сжатия ZIP свободны. Предъявите сравнение полученного снимка и ZIP с R, а также короткое наблюдение создания `git archive`.

Дополнительный документ показывает допустимый вариант состава: можно подготовить выпуск только с обязательными файлами.

Комплект содержит локальный проект отчёта с двумя репозиториями Git и входным патчем. Требуются Git, текстовый редактор и один выбранный маршрут: PowerShell 7/Windows либо fish/Linux.

<a id="начало-работы"></a>

## Начало работы

</div>

Полное условие и открытые примеры доступны на странице задачи «Подготовка выпуска» и в скачиваемом архиве условия `exr-project-maintenance-release-conditions.zip`. Для локального чтения распакуйте архив целиком в отдельную папку и откройте `README.md`.

Имена учебных файлов и регистр букв сохраняйте по условию. Последовательность допустимых действий выбирайте самостоятельно, пояснение создайте текстовым редактором.

## Материалы выпуска

## Полная сдача
